# Развёртывание

## 1. Требования

- Node.js 22 LTS (Vite 8 требует 20.19+ или 22.12+) для основной версии.
- Аккаунт Supabase.
- Репозиторий GitHub.
- Microsoft Edge или другой современный браузер для автономной версии.

Автономному файлу `local/index.html` ничего из перечисленного, кроме браузера, не требуется.

## 2. Supabase

### 2.1. Создание проекта

Создайте проект в Supabase и сохраните:

- Project URL;
- публичный anon key.

Ключ `service_role` не нужен для портала. Не копируйте его в `.env`, GitHub, исходный код или браузер.

### 2.2. Миграции

В SQL Editor последовательно выполните:

1. `supabase/migrations/202610230001_initial_schema.sql` — типы, таблицы, индексы, триггеры и журнал действий.
2. `supabase/migrations/202610230002_rls.sql` — функции ролей, включение RLS, политики и права.

Не меняйте порядок файлов. Оба файла рассчитаны на чистый проект.

### 2.3. Демонстрационные данные

`supabase/seed.sql` — необязательный набор. Он создаёт новости, документы, статьи кодексов, законопроекты, повестку, органы власти и международные карточки. Все такие записи помечены `is_demo = true`, результаты голосований и протоколы отсутствуют.

Для рабочего портала seed можно не выполнять либо удалить демонстрационные записи после наполнения.

### 2.4. Первый администратор

1. Откройте **Authentication → Users**.
2. Создайте пользователя с email и паролем.
3. Скопируйте UUID пользователя.
4. Выполните в SQL Editor:

```sql
update public.profiles
set role = 'admin'
where id = '<UUID-пользователя>';
```

Профиль создаётся автоматически триггером после появления пользователя. Если строки нет, проверьте, что миграция и триггер `on_auth_user_created` применились.

Самостоятельная регистрация не выдаёт роль. Пользователь с ролью `user` видит только публичные материалы, даже если откроет `/admin`.

### 2.5. Проверка

```sql
select count(*) from public.news_posts where status = 'published';
select count(*) from public.legislation_documents;
select count(*) from public.code_articles;
select count(*) from public.bills;
```

Публичный anon-доступ должен возвращать только опубликованные новости, опубликованные голосования, опубликованные заседания и опубликованные международные документы.

## 3. Переменные окружения

Создайте `.env` в корне:

```dotenv
VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR-PUBLIC-ANON-KEY
```

Файл `.env` уже исключён через `.gitignore`.

Для GitHub Actions те же значения добавляются как Variables, а не как секреты с закрытым содержимым:

- **Settings → Secrets and variables → Actions → Variables**;
- `VITE_SUPABASE_URL`;
- `VITE_SUPABASE_ANON_KEY`.

Anon key публичен по назначению: он попадает в браузерную сборку. Его защищает RLS, а не секретность. `service_role` обходит RLS и в клиентской части недопустим.

## 4. Локальный запуск основной версии

```bash
npm ci
npm run dev
```

Dev-сервер открывается по адресу `http://localhost:5173/kf-portal/`: базовый путь по умолчанию равен `/kf-portal/`. Для другого пути задайте `VITE_BASE` перед запуском.

`package-lock.json` включён в проект. `npm ci` устанавливает зафиксированные версии, не изменяя lock-файл. Для добавления новой зависимости используйте `npm install <package>`.

Проверка и production-сборка:

```bash
npm run typecheck
npm run build
npm run preview
```

## 5. GitHub Pages

### 5.1. Загрузка проекта

Создайте репозиторий и загрузите файлы через веб-интерфейс GitHub.

Если каталог `.github` не виден в проводнике Windows, включите отображение скрытых элементов. Если он всё равно не загрузился, создайте файл вручную:

**Add file → Create new file →** `.github/workflows/deploy.yml`

Содержимое скопируйте из локального файла.

Не загружайте:

- `.env`;
- `node_modules`;
- `dist`;
- секретные ключи Supabase.

### 5.2. Настройка Pages

1. **Settings → Pages**.
2. **Build and deployment → Source: GitHub Actions**.
3. Переменные Supabase для текущей статической публикации не требуются.

Workflow `.github/workflows/deploy.yml`:

- копирует `local/index.html` в `dist/index.html`;
- добавляет `favicon.svg` и `.nojekyll`;
- загружает `dist` как Pages artifact;
- публикует сайт через `actions/deploy-pages`.

Запуск происходит при push в `main` или вручную через **Actions → Deploy to GitHub Pages → Run workflow**.

### 5.3. Адрес и базовый путь

Для репозитория проекта адрес обычно выглядит так:

```text
https://<owner>.github.io/<repository>/
```

Сайт использует hash-маршруты, поэтому работает по этому адресу без настройки `VITE_BASE`.

### 5.4. Собственный домен

1. Настройте домен в **Settings → Pages → Custom domain**.
2. Настройте DNS согласно инструкциям GitHub Pages.
3. После смены домена повторно запустите workflow.

## 6. Автономная версия

`local/index.html` используется как источник текущей публикации GitHub Pages. Его также можно:

- открыть двойным щелчком в Edge;
- передать файлом;
- разместить рядом с сайтом как отдельную страницу.

Для проверки отсутствия сети найдите в файле строки `http://`, `https://`, `@import`, `//cdn`. Их быть не должно. Файл не подключается к Supabase, не сохраняет изменения и не содержит секретов.

## 7. Обновление сайта

1. Измените `local/index.html` через веб-интерфейс GitHub или локально.
2. Проверьте файл в Edge, включая мобильную ширину экрана.
3. Отправьте изменения в `main`.
4. Дождитесь завершения workflow.
5. Проверьте опубликованный адрес и жёстко обновите страницу (`Ctrl+F5`) при необходимости.

React-версия из `src/` для текущей публикации не собирается. Её проверка выполняется отдельно через `npm run typecheck` и `npm run build`.

## 8. Диагностика

Диагностика ниже в основном относится к React-версии и ручной сборке. Для текущей статической публикации сначала проверьте, что workflow скопировал `local/index.html` в `dist/index.html`.

### Сайт открывается, но стили или переходы ведут на 404

- Проверьте `VITE_BASE` в workflow.
- Для репозитория проекта путь должен совпадать с именем репозитория.
- Для `<owner>.github.io` и собственного домена используйте `/`.
- Убедитесь, что в `dist` созданы `404.html` и `.nojekyll`.

### Вложенный маршрут открывается напрямую, но показывает 404

`404.html` перенаправляет в SPA. Проверьте, что файл скопирован в `dist` и Pages публикует именно artifact из workflow, а не старую ветку `gh-pages`.

### Сборка падает на `npm ci`

- Проверьте `package.json` и `package-lock.json` на повреждённые символы и BOM.
- Убедитесь, что используется Node.js 22 (минимум 20.19).
- Не редактируйте lock-файл вручную: при необходимости пересоздайте его через `npm install`.

### Публичные разделы пусты

- Проверьте Variables `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
- Пересоберите сайт: Vite встраивает переменные на этапе сборки.
- Выполните миграции и seed либо добавьте реальные опубликованные записи.
- Проверьте RLS: anon должен видеть только разрешённые строки.

### Админпанель сообщает об отсутствии базы

Переменные не попали в сборку. Добавьте их в GitHub Variables и запустите workflow повторно.

### Вход выполнен, но нет прав

Проверьте `profiles.role` для UUID пользователя. Интерфейс может скрыть кнопки, но база всё равно отклонит запись без роли `editor`, `duma` или `admin`.

### Ошибка RLS при сохранении новости

- Пользователь должен иметь роль `editor` или `admin`.
- Профиль должен существовать в `public.profiles`.
- Политики из второго файла миграции должны быть применены.

## 9. Откат

GitHub Pages хранит предыдущие запуски workflow. Для отката:

1. Откройте **Actions → Deploy to GitHub Pages**.
2. Выберите успешный запуск с нужной версией.
3. Повторите deploy или верните предыдущий коммит в `main` и запустите workflow.

Изменения схемы Supabase откатываются отдельными SQL-миграциями. Не удаляйте таблицы с реальными материалами без резервной копии.
